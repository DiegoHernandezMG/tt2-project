Dashboard Web Administrativo

Documentación técnica detallada del sistema web de SerenaMente 2.0 — sitio informativo público y dashboard administrativo para psicólogos — desarrollado con React 19 y Vite, respaldado por Supabase (PostgreSQL, Auth y Edge Functions).

2.1 Descripción general

El sistema web de SerenaMente 2.0 cumple dos funciones complementarias dentro del ecosistema. En primer lugar, expone un sitio público informativo dirigido a usuarios potenciales, donde se describe el programa, se invita a descargar la aplicación móvil mediante un código QR y se ofrece un formulario de contacto. En segundo lugar, integra un dashboard administrativo privado dirigido al equipo clínico que da seguimiento al avance terapéutico de los pacientes registrados en la app móvil.

La aplicación está construida como una Single Page Application con React 19 y Vite 7, desplegada en Vercel, y consume directamente los servicios de Supabase (autenticación, base de datos PostgreSQL y siete Edge Functions escritas en TypeScript sobre Deno). Las operaciones que requieren privilegios elevados — envío de correos, creación de usuarios en Auth, agregación de datos clínicos o eliminación cascada — se delegan a Edge Functions, mientras que las consultas de lectura tabular se realizan directamente desde el cliente mediante el SDK oficial.

ℹ️ El dashboard administrativo y la aplicación móvil comparten la misma base de datos en Supabase. El subsistema 2 únicamente lee y opera sobre los datos generados por la app móvil; no posee flujos terapéuticos propios.

2.3 Arquitectura del proyecto

2.3.1 Estructura de carpetas

El código fuente del cliente se organiza dentro de src/ siguiendo una arquitectura por capas con páginas agrupadas por audiencia: una rama pública (pages/public/) y una rama privada (pages/admin/). Los servicios que encapsulan acceso a datos se aíslan en services/, las utilidades de infraestructura compartida en lib/ y los hooks transversales en hooks/. El backend serverless se encuentra desacoplado en supabase/functions/.

2.3.2 Capas de la aplicación

El cliente separa responsabilidades en cuatro capas bien definidas:

  • Capa de presentación (pages/, components/, layouts/): componentes funcionales que renderizan la UI y delegan toda la lógica de acceso a datos a la capa de servicios.
  • Capa de servicios (services/): funciones puras asíncronas que encapsulan llamadas al SDK de Supabase y a las Edge Functions. Cada función expone una promesa con datos normalizados o lanza una excepción descriptiva.
  • Capa de infraestructura (lib/, hooks/): cliente Supabase singleton, hook de autenticación (useAuth) y constantes de dominio.
  • Capa de backend serverless (supabase/functions/): siete Edge Functions Deno que ejecutan operaciones con privilegios elevados o integraciones con servicios externos (Resend).

2.3.4 Estado y autenticación

La gestión del estado de sesión se centraliza en AuthProvider (definido en src/hooks/use-auth.js) mediante el API de Context de React. Al montarse, el provider:

  1. Llama a adminSupabase.auth.getUser() para recuperar la sesión actual desde el almacenamiento local del navegador (con storageKey: "serenamente-admin-auth").
  2. Si existe un usuario, invoca getCurrentAdminProfile() para validar la fila correspondiente en la tabla admins y derivar el estado (ACTIVE, INVITED_PENDING o SUSPENDED).
  3. Suscribe el listener onAuthStateChange para reaccionar a inicios y cierres de sesión en otras pestañas o tras una redirección OAuth.

El hook useAuth() expone los valores user, profile, loading y refreshProfile a cualquier componente descendiente. La gestión de estado local de páginas y formularios se realiza con useState y useMemo sin librería adicional.

2.4 Web pública

Las páginas públicas comparten el layout PublicLayout, que renderiza la Navbar (logo + enlaces a Inicio, Nosotros, Comenzar, Dudas y un botón de acceso administrativo) y el Footer. La navegación móvil utiliza un drawer lateral montado vía createPortal sobre document.body.

2.4.1 Páginas informativas

Las páginas Home, About y Start son estáticas y se basan en composición de componentes con CSS por módulo. Home incrusta un video institucional desde YouTube y los logos de las instituciones colaboradoras (SUAyED, LabPSIIT, UNAM, ESCOM, IPN). Start guía al usuario a través de tres pasos para descargar la aplicación Android y muestra el código QR de descarga.

2.4.2 Formulario de contacto

La página FAQ incluye un acordeón con las preguntas frecuentes y un formulario de contacto con tres campos: nombre, email y mensaje. Al enviarse, el cliente hace POST a la Edge Function send-contact-email, la cual valida los campos y reenvía la solicitud al servicio Resend para entregar el mensaje en la cuenta institucional serenamente@iztacala.unam.mx.

2.4.3 Verificación de correo (app móvil)

La ruta /mobile-verify-email es el destino al que apunta el enlace mágico emitido por la Edge Function send-verification-email cuando un usuario crea su cuenta desde la app móvil. La página escucha el evento SIGNED_IN de Supabase, cierra la sesión inmediatamente (la app móvil mantendrá su propio token) y muestra una confirmación visual. Si transcurren ocho segundos sin recibir el evento, se renderiza un mensaje de enlace expirado.

2.4.4 Recuperación de contraseña (app móvil)

La ruta /mobile-reset-password recibe el token de recuperación generado por la Edge Function send-reset-email. La página espera al evento PASSWORD_RECOVERY o SIGNED_IN para habilitar el formulario, valida que la nueva contraseña tenga al menos ocho caracteres y coincida con la confirmación, invoca auth.updateUser({ password }) y cierra la sesión web una vez actualizada.

2.5 Autenticación y control de acceso administrativo

2.5.1 Inicio de sesión

La página Login ofrece un formulario clásico de correo y contraseña. El handler handleLogin implementa un timeout defensivo de doce segundos sobre signInWithPassword y un segundo timeout de diez segundos sobre la consulta del perfil. Tras autenticarse, el flujo verifica que el correo exista en la tabla admins y que su estado sea ACTIVE; cualquier otra combinación cierra la sesión y muestra un mensaje específico. Finalmente, registerLoginEvent actualiza last_login_at y registra un evento LOGIN_SUCCESS en audit_logs, y el flujo redirige a /admin/users si el rol es SUPER_ADMIN o a /admin/dashboard en cualquier otro caso.

2.5.2 Activación de cuenta

Cuando un SUPER_ADMIN invita a un nuevo administrador, el cliente inserta una fila en admins con is_active = false y dispara la Edge Function send-invitation-email, la cual envía un correo con un enlace del tipo /admin/activate?email=<encoded>. La página ActivatePage permite al invitado fijar una contraseña (mínimo ocho caracteres) y la envía a la Edge Function activate-admin-account, que crea el usuario en Supabase Auth (o actualiza su contraseña si ya existía) y marca el registro como is_active = true con su auth_user_id definitivo.

2.5.3 Recuperación de contraseña

El propio formulario de login expone un modo "¿Olvidaste tu contraseña?" que envía el correo a la Edge Function send-reset-email. Esa función genera un enlace mágico de recuperación con supabaseAdmin.auth.admin.generateLink, lo encapsula en una plantilla HTML y lo envía vía Resend con el destino redirectTo apuntando a /admin/reset-password. La página ResetPasswordPage espera el evento PASSWORD_RECOVERY y permite establecer la nueva contraseña.

ℹ️ Por seguridad, el formulario siempre muestra el mensaje "si el correo está registrado recibirás un enlace" — sin importar si la dirección existe o no — para evitar enumeración de cuentas.

2.5.4 Protección de rutas

El componente ProtectedRoute envuelve a las rutas privadas y aplica tres verificaciones antes de renderizar a los hijos:

  • Mientras loading esté activo, muestra el mensaje "Cargando…" en lugar de redirigir prematuramente.
  • Si no existe user, redirige a /admin/login.
  • Si requireActive está habilitado (valor por defecto) y el profile.status no es ACTIVE, redirige también al login.
  • Si se especifica allowedRoles y el rol del usuario no pertenece al arreglo, se redirige al dashboard de pacientes.
function ProtectedRoute({ children, allowedRoles = null, requireActive = true }) { const { user, profile, loading } = useAuth(); if (loading) return <p>Cargando...</p>; if (!user) return <Navigate to="/admin/login" />; if (requireActive && profile?.status !== ADMIN_STATUS.ACTIVE) { return <Navigate to="/admin/login" replace />; } if (Array.isArray(allowedRoles) && allowedRoles.length > 0 && !allowedRoles.includes(profile?.role)) { return <Navigate to="/admin/dashboard" replace />; } return children; }

2.7 Dashboard de pacientes

La ruta /admin/dashboard es la pantalla principal del subsistema. Al cargar, el servicio listDashboardProfiles consulta la tabla perfiles y excluye los id_usuario presentes en admins (para que los propios administradores no aparezcan listados como pacientes). El usuario puede seleccionar a un paciente del listado lateral; al hacerlo, el dashboard llama a getPatientData, que delega en la Edge Function get-patient-data.

Datos agregados por paciente

La Edge Function consolida en paralelo siete consultas SQL sobre tablas clínicas y devuelve un objeto único con: evaluaciones inter-nivel (OASIS y ODSIS), progreso por nivel de intervención, ejercicios completados, métricas calculadas por IA del último nivel, total acumulado de accesos, registro de sesión final y emociones de la semana en curso. El componente EmotionChart renderiza una gráfica de barras propia con CSS para visualizar la intensidad emocional diaria.

Exportación a Excel

El dashboard permite exportar a .xlsx tanto a un paciente seleccionado como a todos los pacientes en un solo archivo con una pestaña por persona. La utilidad buildPatientSheet construye la matriz de filas que SheetJS materializa con XLSX.utils.book_append_sheet y XLSX.writeFile. El nombre del archivo incluye la fecha ISO del día.

Eliminación de pacientes

Solo los SUPER_ADMIN ven el botón "Eliminar paciente". El handler invoca la Edge Function delete-patient, que verifica el rol del solicitante, recupera las sesiones del paciente y realiza un borrado en cascada de todas las tablas asociadas (intervención, evaluaciones, seguimiento) antes de eliminar el perfil y, finalmente, la cuenta correspondiente en Supabase Auth.

2.10 Servicios cliente

La capa services/ agrupa las funciones que mediante el SDK de Supabase o un fetch directo materializan las operaciones del subsistema. El cliente Supabase se instancia una sola vez en lib/supabase-admin.js con un storageKey propio (serenamente-admin-auth) para evitar colisiones con otros clientes que pudieran compartir el dominio.

import { createClient } from "@supabase/supabase-js"; const adminSupabaseUrl = import.meta.env.VITE_ADMIN_SUPABASE_URL; export const adminSupabaseAnonKey = import.meta.env.VITE_ADMIN_SUPABASE_ANON_KEY; export const adminSupabase = createClient(adminSupabaseUrl, adminSupabaseAnonKey, { auth: { storageKey: "serenamente-admin-auth" }, });

Servicios principales

  • admin-users.js: gestión completa del ciclo de vida de los administradores (invitar, activar, suspender, reactivar, eliminar, auditar).
  • dashboard.js: listDashboardProfiles() para listar pacientes excluyendo a los administradores y getPatientData(userId) que invoca la Edge Function.

Cada servicio normaliza la entrada (correos en minúsculas, nombres recortados), valida precondiciones del lado del cliente con mensajes en español y propaga errores a la UI con descripciones específicas que las páginas presentan en bloques login-error o activate-error.

2.12 Pruebas de carga y rendimiento

Con el propósito de caracterizar la capacidad operativa del subsistema web bajo carga concurrente y de identificar sus límites prácticos, se llevó a cabo una batería de cuatro pruebas automatizadas sobre el entorno de producción (https://tt2-project.vercel.app) el día 20 de mayo de 2026. Cada prueba se orientó a un componente distinto de la arquitectura: la Edge Function más exigente del backend, el endpoint de autenticación, el flujo autenticado completo y, finalmente, las páginas estáticas servidas desde el CDN de Vercel.

ℹ️ El objetivo de estas pruebas no fue determinar un máximo absoluto del sistema, sino verificar que el rango operativo esperado (50–200 usuarios no simultáneos) se cubre con holgura y describir el comportamiento del sistema cuando se le somete a una concurrencia continua superior a la prevista.

2.12.1 Metodología y herramienta

Las pruebas se ejecutaron con k6 v2.0.0, una herramienta de load testing open source que simula usuarios virtuales (VUs) escribiendo escenarios en JavaScript. Cada VU ejecuta el flujo asignado en bucle continuo durante la duración del escenario, lo cual representa una condición de uso mucho más exigente que el patrón real (donde un administrador realiza acciones espaciadas entre sí). Los scripts utilizados se encuentran versionados en el directorio load-tests/ del repositorio.

Tabla 8. Componentes evaluados en la batería de pruebas

Prueba Componente VUs máximos Capa

Para cada escenario se definieron umbrales de aceptación (thresholds) sobre dos indicadores principales: el percentil 95 del tiempo de respuesta (p95) y la tasa de error global. El cumplimiento o incumplimiento de estos umbrales determina el resultado PASÓ o FALLÓ de la prueba.

La totalidad de los intentos de inicio de sesión falló a partir de los ~46 segundos de ejecución. Los errores observados (connection reset by peer, PROTOCOL_ERROR, request timeout, unexpected EOF) son indicativos del comportamiento defensivo de Supabase Auth ante múltiples intentos de autenticación provenientes de una misma IP.

⚠ Causa identificada — Rate limiting de Supabase Auth. El servicio aplica un límite por IP sobre /auth/v1/token como medida de seguridad contra ataques de fuerza bruta. La prueba reproduce precisamente el patrón que ese mecanismo está diseñado para bloquear (50 logins simultáneos desde la misma dirección de origen).

En consecuencia, este resultado no representa un problema de capacidad del sistema: los administradores inician sesión de forma esporádica (una vez por sesión de trabajo) y la sesión persiste en el navegador durante horas, por lo que el patrón probado no se reproduce en condiciones reales. La conclusión metodológica de esta prueba motivó el diseño de la Prueba 3, que evalúa el flujo autenticado utilizando tokens obtenidos previamente.

Análisis del cuello de botella

El contraste entre ambos endpoints es revelador. La Edge Function mantuvo una tasa de éxito del 96.4% bajo 100 VUs continuos, mientras que el acceso REST directo a la tabla perfiles falló en su totalidad. Los errores observados sobre el endpoint REST (request timeout, connection reset by peer, EOF) son consistentes con la saturación del pool de conexiones de PostgreSQL en el plan gratuito de Supabase, cuyo límite práctico ronda las 50 conexiones concurrentes continuas. Las Edge Functions, en cambio, operan sobre un pool de recursos independiente (runtime Deno) y por ello toleran mejor la concurrencia sostenida.

⚠ Hallazgo principal. Bajo carga continua superior a 50 VUs simultáneos, la API REST de Supabase es el componente más sensible de la arquitectura. Esto no compromete el uso real esperado, pero condiciona el camino de escalamiento futuro: una migración a un plan superior (que amplía el pool de conexiones) o el rediseño del listado de pacientes como Edge Function permitiría sostener mayor concurrencia.

Para los volúmenes contemplados en el alcance de la intervención de telepsicología — donde los administradores no realizan peticiones de forma continua y simultánea desde un único origen — el rendimiento medido es adecuado y deja margen razonable para crecimiento. Las rutas de escalamiento identificadas (upgrade del plan de Supabase, rediseño del listado como Edge Function, o migración del hosting estático a los servidores de la UNAM) quedan documentadas como trabajo futuro.
